## Статус

Получен рабочий кандидат NeoForge-порта с автоматическими и runtime-проверками основных операций.

## Миграция API и поведения

| Участок | Изменение |
|---|---|
| Gradle | NeoGradle заменён на ModDevGradle; Java 25; сборка только `neoforge`, с исходниками `common`; отключены публикационные плагины |
| `Stxck` | `ResourceLocation` → `Identifier`, ключ измерения → `identifier()`; суммы считаются как `long`, резерв остаётся совместимым `int` |
| Синхронизация | Собственный ID `SynchedEntityData` заменён на зарегистрированный syncable NeoForge attachment `extra_item_count` с `VAR_INT`; обновления отключены во время удаления и после удаления сущности |
| `ItemEntityMixin` | Удалены отсутствующие constructor targets; актуальные `tick`, `setItem`, `tryToMerge`, `ValueInput` / `ValueOutput`; обязательные injection points проверены в игре |
| `ItemEntityAccessor` | Сохранены age/pickupDelay; добавлены invoker локального поиска и доступ к штатному DATA_ITEM для очистки старой ссылки |
| `ItemStackAccessor` | Больше не нужен: тип и компоненты скрытого остатка хранит независимый шаблон; лимит берётся из `ItemStack.getMaxStackSize()` |
| `EventHandler` | Только серверная логика; ограниченный AABB; исключены удалённые, неподходящие и временно занятые сущности |
| `ClientPacketListenerMixin` | Удалён обоснованно: исходная сущность больше не воскрешается после успешного извлечения, обычные take/remove/spawn пакеты корректны; проверен реальный клиентский подбор |
| `LevelRendererMixin`, `ItemCountRenderer` | Заменены на извлечение данных `ItemEntityRenderState` и `SubmitNodeCollector.submitText`; нет отдельного прохода по всем предметам для текста |
| `StxckNeoForgeInitializer` | Регистрация attachment на mod bus, актуальный EntityJoinLevelEvent и ModConfigSpec |
| Фильтры | Сохранены имена конфигураций; в `itemList` поддержаны также `#namespace:tag`, изменения списка не остаются в устаревшем кэше |

NeoForge 26.1.2 в dev-режиме отвергает добавление чужих entity data IDs через Mixin. Это обнаружено
реальным запуском, затем исправлено через [официальный механизм attachments](https://docs.neoforged.net/docs/datastorage/attachments/),
а не отключением проверки NeoForge или обязательных Mixins.

Сохранён ключ `StxckExtraItemCount`. Дополнительный `StxckExtraItemTemplate` защищает исходные
компоненты резерва, если другой мод меняет видимый стек непосредственно перед сохранением.
Старые данные без нового поля читаются. `maxSize` теперь ограничивает **общую численность кучи**,
а не только резерв. Уже сохранённые большие кучи не обрезаются. Нестандартные entity types,
унаследованные от ItemEntity, исключены из расширенного слияния: их поведение нельзя безопасно
перенести в обычную сущность остатка.

Успешное извлечение удаляет старую сущность и очищает её ItemStack. Резерв получает новый UUID.
Если другой мод отменяет создание остатка, пустая старая сущность сохраняет резерв для повторной
попытки. Обратное слияние в неё во время операции запрещено. Подробный разбор и проверенные
инварианты: [NO_DUPES.md](verification/NO_DUPES.md).

- Финальный JAR загружен dedicated server до **Done**.
- **6 149 успешных проверок**: слияние, извлечение, сохранение, лимиты, фильтры, разные компоненты,
  damage, нестакуемые предметы, отмена создания остатка, законное уничтожение и despawn.
- Две настоящие тикающие воронки: **640 в инвентарях + 360 на земле = 1 000**.
- Отдельный процесс сохранения и отдельный процесс загрузки: **1 000** предметов и имя сохранены.
- Чанк действительно выгружался: тест проверяет отсутствие UUID в загруженном мире; после
  загрузки восстановлена ровно одна куча из **1 000** предметов.
- Клиент Minecraft под Xvfb/llvmpipe подключается к отдельному dedicated server, видит синхронизированную
  кучу `1000` (оверлей `16x` в исходном режиме STACK_COUNT), затем подбирает ровно **1 000**.
  Сервер и клиент независимо проверяют количество в инвентаре.
- MineColonies: реальный `CitizenItemUtils.tryPickupItemEntity` и `InventoryCitizen`, тестовая
  `ICitizenData`: **1 000 в инвентаре, 0 на земле**, повторная старая ссылка не дублирует предметы.
  Это компонентная интеграция, не симуляция рабочих заданий, строительства или AI колонии.

Доказательства и инструкции: [verification/README.md](verification/README.md),
[evidence](verification/evidence). В финальных основных прогонах проверяются MixinApplyError,

из локальных портов MineColonies и библиотек сохранены в их интеграционном логе; они не выдаются
за ошибки Stxck или за доказательство полной готовности самих этих портов.

Для [Create issue #18](https://github.com/frank89722/Staaaaaaaaaaaack/issues/18) добавлена проверка
двух настоящих FunnelBlock (Andesite и Brass отдельно), двух barrel-инвентарей и повторного вызова
обработчика со старой ссылкой: ровно 1000 предметов, компоненты сохранены. Дополнительно проверены реальные обработчики chute, неподвижного belt и fan blasting:

## Deferred Merge и серверная производительность

Таблица ниже — историческое сравнение FI / NeoForge .109 до защиты post-spawn наград.
Итоговые прогоны NL / .114 записываются отдельно и не сравниваются напрямую с FI.

`mergeDelayTicks=0` — немедленное слияние; `10` — разрешение слияния после задержки.
Задержка не меняет pickupDelay и не запрещает подбор игроком или механизмом.
При наступлении срока выполняется один дополнительный локальный поиск. Готовность соседей
учитывает общее игровое время, поэтому порядок обработки сущностей одного тика не вызывает
многократный поиск по ещё не обработанным предметам.

Глобального сканирования предметов каждый тик нет. Используется пространственный поиск самого
Level в ограниченном AABB и обычная периодичность ItemEntity; производственный мод не создаёт
chunk tickets и не загружает соседние чанки. Отдельный spatial index не добавлялся.

Условия: одиночные одинаковые предметы в одной точке, без движения/гравитации; по 100 серверных
тиков на сценарий; JVM `-Xmx1G`, без клиента. Ванильная строка — **NeoForge без Stxck**, только
проверочный мод. MSPT включает нагрузку до слияния; время создания сущностей отдельно в CSV.
CPU — суммарное время серверного потока за 100 тиков. Heap — максимум занятой Java heap, не RSS
и не оценка памяти «на предмет». Общий сервер FI выполняет и другие задачи: результаты однократные,
не статистически контролируемые; нельзя переносить точные коэффициенты на другую сборку.

В историческом прогоне FI немедленное слияние происходило при добавлении в мир. В итоговой
реализации новая сущность впервые объединяется на первом тике: вызывающий код должен успеть
установить owner, компоненты и makeFakeItem после addFreshEntity. PickupDelay не изменяется. Ванильные кучи остаются ограниченными размером стака.

До изменения Deferred Merge неподвижные сущности ожидали штатного поиска до 40-го тика;
после изменения объединяются на 10-м. Для 5 000 предметов до изменения получено 536,11 MSPT,
после — значение в таблице. Рекомендация для большой нагрузки: **оставить задержку отключённой**.
Она функционально проходит тесты, но удерживает много сущностей до объединения и может вызвать
заметный лаг при массовом выбросе.

Дополнительный прогон Stxck с выключенным расширенным слиянием через пустой whitelist достиг
watchdog 120 секунд на 5 000 сущностях в одной точке. Стек показывает ванильный `Entity.collide` /
`getEntityCollisions`. Это **не успешный тест**; его лог сохранён отдельно. Основной независимый
ванильный baseline и оба рабочих режима измерены отдельно. Сложная дополнительная индексация
поиска слияния не решила бы саму нагрузку ванильных столкновений до объединения.

## Ограничения и настройки для сборки

- Не проверены полная движущаяся фабрика Create и воздушные потоки, живая ME-сеть и Import Bus AE2,
  UI GachaAddiction, Mekanism, MI, Ender IO и Lootr.
- У MineColonies проверен подбор и инвентарь, но не полный AI, рабочие задания и строительство.
- Не выполнен длительный soak-тест полной сборки и тест на реальном пользовательском GPU.
- Не заявлена поддержка модов, которые обходят ItemEntity API и самостоятельно повторно копируют
  уже полученные предметы, или нестандартных ItemEntity entity types.
- Производительность Deferred Merge на очень плотных массовых выбросах хуже немедленного режима.
- Fabric на этой ветке не собирается. Данные для старого Stxck читаются; обратный downgrade не тестировался.

Предлагаемые начальные настройки находятся в [recommended-config](verification/recommended-config):
горизонтальный радиус **0.5**, вертикальный **0**, максимум **65 536**, задержка **0**,
нестакуемые предметы **false**; клиентский радиус **8**, масштаб **0.8**, режим **ITEM_COUNT**.
Меньший горизонтальный радиус уменьшает риск объединения соседних технологических потоков.
Это рекомендованный стартовый профиль, а не автоматически применённая конфигурация production.
Профилирование выше выполнялось с исходным горизонтальным радиусом **1.25**.

Правила спавна мобов, HNN, FTB Chunks и сторонние репозитории не изменялись.
